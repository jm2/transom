# 0001 — FreeRDP 3 bindings: our own bindgen layer over the system library

- Status: accepted
- Date: 2026-11-21

## Context

`transom-view-freerdp` needs Rust access to FreeRDP 3's client API: context and
entry points, settings, GDI, the GFX and Display Control channels, pointer
callbacks and input. Options considered:

1. **`freerdp2` / `freerdp2-sys`** (elmarco/freerdp-rs, used by RDW). FreeRDP **2**
   only. FreeRDP 2 is end-of-life and lacks the 3.x settings API, AAD and the
   current GFX/H.264 fixes. Rejected.
2. **`freerdp-sys` 0.1.0** (crates.io). FreeRDP 3, but a single release by one
   author, a vendored CMake build by default and a bindings surface we don't
   control. Adopting it adds a supply-chain dependency for something we can generate
   in about 100 lines. Rejected for now; we can revisit if it matures.
3. **Our own `bindgen` run at build time against the system FreeRDP 3**, found with
   `pkg-config`. **Chosen.**

## Decision

- `crates/transom-view-freerdp/build.rs` runs `bindgen` over `src/wrapper.h` with an
  allowlist (`freerdp_*`, `gdi_*`, `PubSub_*`, WinPR events and waits, the settings
  key enums, display-control and GFX types). The output lives in `OUT_DIR` and isn't
  checked in.
- The library is found with `pkg-config` (`freerdp3`, `freerdp-client3`, `winpr3`).
  The same mechanism works on Linux distros, Flatpak (`org.gnome.Sdk` with FreeRDP
  built as a module), macOS (Homebrew `freerdp`) and Windows (vcpkg `freerdp`, or
  MSYS2). This keeps ADR 0002 (cross-platform) viable.
- The minimum supported FreeRDP is **3.10**. Development started on 3.33.1 (Fedora 45).
- All `unsafe` stays in `transom-view-freerdp` (PLAN §9). The rest of the crate exposes
  only the safe `transom_view_core::engine::RdpEngine` implementation.

## Consequences

- Building needs libclang (Fedora: `clang-devel`; macOS: Xcode CLT; Windows: LLVM).
  If that becomes a packaging burden, add a `pregenerated` feature that ships
  bindings per target, regenerated by a script.
- FreeRDP's ABI is stable within 3.x, and generating at build time tracks any header
  changes automatically.
- We own the certificate flow. FreeRDP validates against the system CA and calls our
  `VerifyCertificateEx` only when that fails. We point `FreeRDP_ConfigPath` at a
  Transom-private directory so FreeRDP's own `known_hosts2` (shared with `xfreerdp`)
  never short-circuits our TOFU store, and we always answer "accept for this session"
  (2) once our store or the user has decided.
